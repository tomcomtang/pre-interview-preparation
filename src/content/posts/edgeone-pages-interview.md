## 1. 项目背景（约 50 秒）

当时腾讯云已经有大量用户在用 **CDN** 和 **EdgeOne 边缘计算**。典型场景是：官网、活动页、文档站走 CDN 加速；有动态逻辑的再自己配边缘函数或回源到一台 Node。痛点也很集中：控制台是按桶、域名、证书、函数来的，前端同学仍然要自己接 Git、构建、上传、配回源；静态和动态是两套产品，SSR / API 还得自己拼；没有「每次 push 一个可访问地址」，预览和生产靠人肉。资源在，开发者托管这一层不在。

我自己用 Cloudflare Pages 时，对比更清楚。那边是开发者心智：绑 Git、自动构建、Preview URL、Workers 跑函数。但海外方案有硬限制：国内访问链路不稳定，账号和结算不在腾讯云体系里，面向国内用户的站点还要备案和合规，没法把现有腾讯云 CDN 流量和账号直接接过去。国内用户等于「知道体验该长什么样，但用不了那套底座」。

所以我规划做一个跑在腾讯云上的托管平台，也就是后来的 EdgeOne Pages：复用已有 CDN 和边缘计算，补上 Git 到 URL 这一层——自动构建、分配域名、静态走 CDN、SSR / API 走边缘函数，用户不用自己买主机、配 Nginx。我在其中做产品规划，以及后面几块的技术落地。

口述收口：

> CDN 和边缘计算的用户已经很多，缺的是开发者托管。Cloudflare 验证了体验，但海外底座进不来。Pages 就是把这层做在腾讯云上。

## 2. 我做的模块（约 2 分钟，由易到难）

能力是一层叠一层的：先让 GitHub 上的静态站能上线，再支持 SSR/API，再用 CLI 补本地和 CI，再靠适配器吃进主流框架，最后用模板和教程把最佳实践交出去。

### GitHub 静态资源部署

第一层，也是大多数人的第一条路径。项目绑定 GitHub，push 后按 **commit SHA** 拉代码、构建，产物写成一次**不可变 Deployment**。访问不是「给项目一台机器」，而是给这次部署挂域名：**提交级 URL 永远指向这一次构建；分支 URL 始终跟最新提交；生产域只是别名指针**。主干推进生产别名，其它分支出 Preview。回滚改指针，不重建。SPA 刷新 fallback 到 `index.html`。这一层把「push 就能访问」跑通，用的就是现成的 CDN。

构建失败时日志很长，PR 上除了红勾和预览链接，可以用模型把「哪一步挂了、可能改哪」压成几句回写到评论里——还是同一条 GitHub Deployment 闭环，不另做产品。仓库构建命令不明确时，也可以根据 `package.json` / README 给出建议命令，降低第一次接入成本。

### 全栈部署方案

静态不够。页面还有 SSR 和 API。在静态方案上增加产物约定：静态继续走 CDN，动态入口打成 EdgeOne 函数，再带一份路由表（哪些 path 走文件、哪些走函数）。访问时边缘用 Host 找到这次部署，按路由表分发。预览和生产环境变量隔离。这一层把已有的边缘计算接进同一套部署，而不再是「前面静态、后面自己找一台 Node」。

函数这条能力要能 **流式写出**，不能等整段响应结束再返回：对话页、生成式接口都是边算边推；密钥只放在函数侧的 env 里，Preview 和生产拆开。实现上就是 Function 透传 `text/event-stream`、禁止边缘把流攒成静态缓存——和 SSR 流式是同一条管道，对话只是把它用满的场景。

### 脚手架（CLI）

Git 是主路径，但 CI 和本地发布还要终端。CLI 做登录、关联项目、构建、发布；本地产出和 Git 云构建同一套产物，增量上传，传完再切生效版本。`dev` 要尽量贴近线上路由，而不是只起一个静态服务。

脚手架还可以把「选模板、填环境变量、第一次发布」收成更短的路径：用自然语言描述要做的站，匹配到模板再 `deploy` 出 Preview URL。生成的仍是普通项目，走同一套 Output，没有第二套发布协议。

### 框架适配器

用户按 Next / Nuxt / Astro 官方方式构建，不会按我们的目录打包。适配器读各框架的路由清单，翻译成「静态 + 函数 + 路由表」。构建期搬对文件；运行时还要把边缘 HTTP 转成框架认识的 request（Host、cookie、body、流式），否则 SSR 和 POST 会 silently 错。加一个框架，等于加一个适配器，平台运行时不用改。

这里的「流式」对适配器是硬要求：Route Handler 若被包装层 buffer 掉，对话接口会表现成「卡几秒再整段弹出」。排障时 Location 跳 localhost 和 SSE 被缓存，都是包装层的问题。

### 场景模板与最佳实践

前面四层能跑之后，用模板和教程降低使用成本。模板按场景（官网、博客、电商、SaaS、对话/生成）和框架提供一键部署，每个模板必须走通静态或全栈链路，等于平台验收件。对话类模板用来验收「函数流式 + Key 在服务端 + Preview 隔离」。模板上可以提供「按说明改一版再部署」，改的是模板代码，发布仍走 Git/CLI。再配文档：何时用静态、何时上函数、环境变量怎么分、SPA 如何避免刷新 404、流式接口不要走 HTML 缓存。

主动陈述到此停。可以说一句：先静态、再全栈，CLI 和适配器是把能力接出去，模板是把最佳实践固化下来。

### 这些 AI 从哪来的（对照你自己的产品，不是另做 AI 平台）

只加强 **已经在讲的模块**，不新增「我们做了大模型」。下面「可参考」仅当实现细节碰巧同类时用，陈述不要先报别人的产品名。

| 你的产品细节 | 为什么能用到 AI | 陈述里怎么带 | 实现时可参考的做法 |
| --- | --- | --- | --- |
| GitHub：PR 评论 + Check + 构建日志 | 失败日志人看不动，但闭环已经在 GitHub 上 | 「红勾旁用模型总结失败原因」 | 失败后调模型，结果写进已有 PR comment / Check output，不另做 IM |
| GitHub：Framework Preset / 构建命令 | 第一次接入最怕不会填 build | 「根据仓库内容建议构建命令」 | 先规则（package.json、框架指纹），规则不够再模型读 README；仍钉死 SHA 构建 |
| 全栈：边缘函数 + 路由 | 动态接口会有长耗时、边生成边下发 | 「函数必须流式，Key 只在服务端 env」 | 响应 `text/event-stream`，禁用对该 path 的 HTML 缓存；超时按生成场景单独配。对话页只是这条能力的验收用例 |
| 适配器：请求包装、流式透传 | 框架 Route Handler 被 buffer 就会静默错 | 「包装层不能把流攒完再返回」 | 与 SSR streaming 同一管道；查 `X-Accel-Buffering`、Transfer-Encoding |

| 构建隔离（追问） | 云构建本就是跑不可信代码 | 不必主动讲 AI | 沙箱、出网白名单、只收 Output；若以后有「生成代码再发布」，复用这套，不新发明 |

## 3. 追问用：技术细节（不主动讲）

### GitHub 静态资源部署

这条链路的本质先记一句（被问「怎么自动更新还能访问」时先抛这个）：

> 构建产出的是不可变快照；用户访问的是 Host 到快照的别名。Git 只负责在某个 SHA 上生产快照，并决定哪个 Host 该指过去。

---

**关联 GitHub 时平台到底拿到了什么？**  
不是在仓库里塞一个普通 webhook URL 就完事。用 GitHub App 装到用户的 org/仓库，换到的是**安装令牌**：clone 私有仓、在 PR 上评论、写 Commit Status、调 GitHub Deployments API。Webhook 必须验签名（HMAC），防伪造 push。权限最小化：contents + deployments + pull requests，不要要整个 org 写权限。

**事件来了之后怎么构建？为什么必须钉死 SHA？**  
payload 里带 `after` / `head_sha`。clone **这个 SHA**，不要 `git pull` 分支头——webhook 到达时分支可能又往前走了。浅克隆即可。同一 SHA 已成功部署过就复用那次 Deployment，不必再建一遍（force-push 改写历史除外）。

**三类 URL 分别是什么？这是访问模型的核心。**

| 类型 | 形态（示意） | 语义 |
| --- | --- | --- |
| 部署 URL | `{项目}-{hash}.pages.xxx` | 钉死这一次构建，发给测试、写进 GitHub Deployment 的 `target_url` |
| 分支 URL | `{项目}-git-{分支}.pages.xxx` | 别名，始终指向该分支**最新成功**的部署，适合丢给同事 review |
| 生产 URL | `{项目}.pages.xxx` + 自定义域 | 别名，只指向当前生产 Deployment |

边缘侧是泛解析 `*.pages.xxx` + 通配证书。请求进来看 `Host`：先查别名表得到 Deployment ID，再取该 ID 下的静态文件。**没有「这个项目的源站」**，只有「这个主机名此刻指向哪次快照」。

**生产域名什么时候切？失败会不会把线网上打挂？**  
产物全部上传成功、健康检查过了，才把生产别名原子切过去。构建失败、取消，别名不动。回滚 = 把别名指回上一次成功的 Deployment，CDN 上旧文件还在，所以能秒切。Git 上 `revert` 合进主干，会再构建一次新快照再切；控制台点回滚则不必等构建。

**GitHub 上用户怎么「看见」这次访问地址？**  
走 GitHub Deployments API，而不是只在群里发一条链接：

1. 收到 push 先建一条 Deployment，状态 `pending`；  
2. 构建中 `in_progress`；  
3. 成功则 `success`，`target_url` 填**部署 URL**（不可变），PR Checks 变绿；  
4. 在 PR 留评：Visit Preview 走**分支 URL**（永远最新），View Deployment 走这次 hash。  

下游 E2E（Playwright 等）应订阅 `deployment_status`，用 `target_url` 打真实预览，而不是猜域名。

**同一分支连续 push，队列怎么排？**  
同分支已有构建：让当前这次跑完；期间进来的提交进队；当前结束后只跑**队尾最新 SHA**，中间的取消。保证预览永远是最新代码，又不会每个字母都占满构建机。取消的构建不切别名。

**Fork 来的 PR 为什么不能自动部署？**  
Fork 的代码不可信，构建机里有 Preview 环境变量。默认要仓库成员点一次授权再构建，避免密钥随 PR 被 `console.log` 出去。内部仓可关，外部开源仓必须开。

**谁不该被构建？**  
忽略构建步骤：只改文档/指定目录则跳过（注意退出码约定：0 跳过，非 0 才构建，和普通 shell 相反）。`[skip ci]` 同类提交可跳过。Monorepo 配 Root Directory，只在该目录有 diff 时构建。跳过仍要回写 GitHub 状态，否则 PR 会一直黄着。

**证书和 Host 有哪些坑？**  
平台子域用一张 `*.pages.xxx` 通配证书，新预览不用等签发。自定义域要 DNS 校验后再签证书，没 ready 前不要切别名。子域 DNS 标签最长 63 字符，分支名过长要截断。分支名若长得像 `www-bank-com` 这类钓鱼形态，要改写，避免浏览器拦截。

**Preview 默认公网可开，安全怎么收？**  
个人项目可以公开预览。企业预览要密码 / 登录墙，否则未发布功能和 Preview env 会随链接泄露。防护发生在边缘看 Host 之后、读文件之前。

**静态资源怎么从仓库到 CDN？**  
构建机跑用户的 install / build，输出目录按 **Deployment ID + 路径** 写入边缘存储。Content-hash 文件可长期缓存；HTML 缓存要短或按部署失效，否则别名切了用户还吃到旧 `index.html`。上传齐了再写别名，禁止边传边切。

**静态站刷新 404 怎么处理？**  
filesystem 未命中再 rewrite 到该 Deployment 的 `index.html`。已有 `about.html` 的 SSG 必须先命中文件。

**和直接用 COS + CDN 差在哪？**  
桶没有：按 SHA 的不可变快照、三类 URL、GitHub Checks、失败不切生产、秒级回滚。这一层就已经是「仓库到 URL」；函数只是同一套别名模型上再挂计算。

### 全栈部署方案

**访问一个页面时请求怎么走？**  
DNS 到 EdgeOne → Host 解析出项目和 Deployment → 执行该次路由表：redirect / rewrite / middleware → 静态命中走 CDN → 未命中进函数 → 再没有则 SPA fallback 或 404。代理查的是「这次部署的表」，不是一台固定源站。

**函数部署后如何被调用？**  
构建产出函数包 + 路径映射（`/api/hello`、`/blog/:slug`）。请求匹配到函数 ID，边缘拉包进 Isolate / Node，用 Fetch 入口执行，把 Response 写回。可缓存的响应（含 ISR）由边缘按 TTL 再出，不必每次冷启动。函数按 Deployment 隔离，预览打不到生产代码。

**为什么分 Edge 和 Node？**  
Edge 近用户、冷启动小，适合 middleware、轻逻辑；没有完整 `fs`。Node 能跑框架官方 server 和大部分 npm，适合重 SSR。适配器按路径选 runtime。

---

### CLI

**和 Git 部署如何保证产物一致？**  
两边都产出同一套 Output（static / functions / routes）。CLI 相当于本地或 CI 里的预构建再上传；云构建是平台代跑。运行时只认 Output，不认构建发生在哪。

**大项目上传怎么做？**  
文件 content hash 比对，只传增量；小文件限并发，大文件分片；全部成功再切指针，避免半份部署被访问。

**`dev` 为什么不能只起静态服务？**  
线上有路由表和函数包装。本地若只 `serve dist`，Host、rewrite、SSR 对不齐，会「本地过了线上挂」。dev 要尽量模拟边缘路由和函数入口。

---

### 适配器

**Next 的 App Router 怎么适配？**  
读 `routes-manifest`、`prerender-manifest` 等清单，按 path 分类：静态 HTML 进 CDN，SSR / Route Handler 进函数，ISR 带缓存 TTL，middleware 进边缘。不解析 RSC 源码，渲染仍在 Next 打出的 server runtime 里。

**「请求适配」指什么？**  
边缘拿到的是 Fetch `Request`，框架可能要 Node 的 `IncomingMessage`，或正确的公网 URL。包装层必须对齐：

1. `request.url` 是用户访问的 Host，不能是内部路径或 localhost；  
2. `x-forwarded-proto/host/for`，否则 redirect 和绝对链接错；  
3. body 只能读一次，POST / Server Action 要缓冲；  
4. 多条 `Set-Cookie` 不能被合并丢；  
5. 流式响应当管道，不能整包再返回；  
6. `/_next/static` 必须走静态，不能进 SSR 函数。

只做构建搬运、不做这层，线上常见 404、跳转错误、空 POST。

**Nuxt / Astro 呢？**  
同一契约，不同翻译。Nuxt 读 Nitro 产物；Astro 静态进 CDN，`output: 'server'` 走官方 adapter 把 SSR 打成函数。平台只认 Output，加框架等于加适配器。

**框架自带 redirect 和平台路由冲突？**  
约定平台 `edgeone.json` 与适配器编译结果合并，单一路由表下发边缘，避免两套规则同时生效。

### 场景模板与最佳实践

**模板和普通示例仓有什么区别？**  
上架标准：能预览、能一键部署、必须走平台产物约定。框架升级先打模板再放量。它既是货架，也是静态/全栈/适配器的 E2E。

**一键部署怎么做？**  
GitHub API fork 模板仓，创建 Pages 项目并触发首次构建。环境变量写入对应环境（Preview / Production），不进仓库。

**最佳实践教程写什么？**  
和产品能力对齐，不写空泛入门：静态 vs 全栈怎么选、Git 与 CLI 分别何时用、环境变量如何隔离、SPA fallback、函数超时与冷启动。教程指向可部署的模板，模板回链文档，形成同一条路径。

## 4. 架构师岗我会追问的难点（听完介绍后）

听完「Git 自动部署 + 三类 URL + 函数 + 适配器」，高级岗确认你是否真做过链路；架构师盯 **一致性、失败模式、多租户、框架升级谁买单**。每题先看清场景和细节点，再背解答。

### 发布与一致性

#### 别名已经切到新部署，用户为什么还能看到旧页面，甚至白屏？

**场景**  
主干刚合并，生产域 `www.example.com` 已指向 Deployment B。客服反馈：有人看到新文案，有人点进去 JS 报错白屏；过几分钟又好了。你打开自己的浏览器是正常的。

**细节点**  
面试官在问：你有没有把「别名指针」和「CDN 缓存」当成两件事。生产域切的是 Host → Deployment ID；用户真正拿到的 HTML/JS 还受 Cache-Control、是否按部署隔离缓存、HTML 与 hashed chunk 是否来自同一次构建影响。

**解答**  
典型裂开是这样发生的：Deployment A 的 `index.html` 里写着 `/_next/static/chunks/app.aaa.js`；B 构建后 chunk 变成 `app.bbb.js`，`aaa` 在 B 的存储里不存在。别名已经指向 B，但某 PoP 对 `/` 仍缓存着 A 的 HTML（缓存 key 只是 URL，没有 Deployment ID）。浏览器用这份旧 HTML 去拉 `app.aaa.js`，B 上 404，白屏。另一种：HTML 是新的，但 Service Worker / 浏览器缓存了旧文档。

做法分三层：

1. **带 hash 的静态资源**（JS/CSS/字体）cache key 可以是 URL，`Cache-Control: public, max-age=immutable`，因为文件名变了就是新资源。  
2. **HTML 和路由元数据**必须按 Deployment 隔离或切流时主动失效。缓存 key 带 Deployment ID，或 TTL 极短，或 purge 该 Host 的 HTML。  
3. **Skew protection（更完整）**：HTML 响应带当前 Deployment；后续 `/_next/static` 请求也带到同一 ID，边缘用「发出这份 HTML 的那次部署」取文件，而不是「此刻生产别名」。这样旧标签页不会去新部署里找已经不存在的 chunk。

口答收一句：**切别名只改「下次未缓存请求去哪」；已经缓存在边缘和浏览器里的 HTML 不会自动跟着走。**

#### 静态文件和函数包不是一起 ready，中间那几秒用户会怎样？

**场景**  
全栈 Next 应用。构建机先把函数包发到计算节点（SSR 已经能跑），静态目录还在上传。这时生产别名被脚本抢先切过去了。用户打开首页，SSR 返回的 HTML 里全是 `/_next/static/chunks/*.js`，这些文件 404。

**细节点**  
一次 Deployment 有三份制品：**静态对象、函数包、路由表**。别名是第四份——控制面指针。面试官要听你有没有「发布事务」：四份里指针最后写；回滚是四份一起回到上一 ID，而不是只回 HTML。

**解答**  
用户感知就是间歇性 404、样式丢失、API 偶发打到旧函数。更糟的是函数已经是新代码、静态还是旧 chunk，运行时 hydration 对不上。

发布协议应是：

1. 上传静态到 `/{deploymentId}/static/...`，确认各区域可读（至少写后读成功，最好有跨区域复制完成信号）。  
2. 发布函数包到同一 Deployment ID，只读探测一次（命中一条 health 或冷启动探针）。  
3. 下发该次路由表到边缘，确认能查到。  
4. **最后**把生产 / 分支别名指向这个 ID。  

任何一步失败：别名不动，这次部署标 failed，GitHub Check 红。回滚：别名指回上一成功 ID，三份旧制品都还在，不需要重新上传。禁止「函数先切、静态后切」这种部分发布。

#### 别名表怎么同步到所有边缘节点？会不会有的节点新、有的节点旧？

**场景**  
全球 / 全国多 PoP。你在控制台看到生产已切到 B，但华南用户仍打到 A，华北已经是 B。持续十几秒。面试官追问：元数据中心挂了，正在访问的站点会不会全军 5xx？

**细节点**  
别名是控制面，要复制到数据面（每个边缘节点）。没有跨地域的分布式事务能让所有 PoP 同一毫秒切换。要区分 **可接受的短暂双版本** 和 **不可接受的「指针新、文件没有」**。还要区分读路径（用户访问）和写路径（新部署）。

**解答**  
同步一般是：控制面写入「权威别名表」（比如带版本号的 KV），边缘定期 pull 或收到 pub/sub 后更新本地缓存。窗口期内，有的 PoP 别名是 A，有的是 B——对生产域可以接受，因为 A、B 都是完整快照，用户只是看到新旧两个完整版本，不是半成品。部署 URL（带 hash 的那条）始终指向固定 ID，测试和 GitHub `target_url` 不受这个窗口影响。

不可接受：PoP 已把别名改成 B，但 B 的静态还没复制到这个区域，于是 404。所以切流顺序必须是 **制品全网可读 → 再推别名**，而不是反的。

元数据存储宕机：读路径 **fail-open**，边缘继续用本地缓存的别名和路由表，站点还能开；写路径（新 Git push）可以失败并告警。不要为了「强一致」在查不到别名时对所有 Host 返回 5xx。

#### GitHub webhook 会重放，构建会不会发两次、切两次生产？

**场景**  
GitHub 超时没收到 200，10 秒后重放同一条 `push`。或用户点「Redeploy」，同时又有一次相同 SHA 的 hook。生产别名被切了两次，构建队列里两个任务抢同一 SHA。

**细节点**  
Webhook 是 at-least-once。幂等键不能是「仓库名 + 分支」——同一分支两个不同 SHA 必须都构建。也不能只靠「正在构建就丢弃」——那会丢最新提交。

**解答**  
幂等键用 GitHub `X-GitHub-Delivery`，或 `installation + repo + SHA + 目标环境（preview/production）`。

- 该 SHA 已有成功 Deployment：直接返回旧 ID，刷新 GitHub Status，**不要**再切一次生产（除非这是一次显式 Promote）。  
- 该 SHA 正在构建：第二个事件并入同一个 job，不新开构建机。  
- 同分支不同 SHA：走队列策略（当前跑完，只跑队尾最新），不要两个生产切流打架。  

切生产必须带条件更新：`if current_alias.sha != new.sha then swap`，并记录操作者是 hook 还是人。重放 hook 撞上「已经是这个 SHA」就是 no-op。

### 多租户与安全

#### 一个客户的函数 while(true)，会不会把节点上别人的站拖死？

**场景**  
客户在 Edge/Node 函数里写了死循环，或 SSR 里同步打了无超时的下游。同一物理节点上还跑着别的租户的函数和静态出站。CPU 打满，邻居站点 TTFB 从 50ms 变成 3s。构建侧：大客户一次 `npm install` 吃光所有构建槽，别人 push 排队半小时。

**细节点**  
多租户有两条伤害面：**运行时**（函数抢 CPU/内存/连接）和 **构建时**（队列、磁盘、出网）。面试官要听隔离单位是进程、容器还是 Isolate，以及配额是按请求、按租户还是按 Deployment。

**解答**  
运行时：每个 Deployment 的函数在独立 Isolate / 进程里，设 CPU 时间、内存、墙钟 `maxDuration`。到点杀执行单元，不影响邻居。单租户并发上限（同时 inflight 请求数），超出排队或 429，避免一个爆火活动占满节点。静态出站走 CDN，不和函数抢同一计算进程。

构建时：每租户并发构建数（例如同时 1～2 个），超出排队；单次构建超时和磁盘上限；不要让「一个 monorepo 装依赖」阻塞全平台。

监控：按租户看 CPU、超时率、构建等待时长；打到阈值告警到平台值班，而不是等邻居客户来投诉「你们挂了」。

#### 构建机在跑用户的 `npm install`，等于执行不可信代码。怎么隔离？

**场景**  
用户 `package.json` 里有一条 `postinstall` 扫环境变量、反连内网 Redis、在镜像里挖矿，或把 Preview 的 `DATABASE_URL` 打印到构建日志（日志对团队只读成员可见）。

**细节点**  
云构建 = 在你的基础设施上跑陌生人的 Node。这是供应链问题，不是「注意一下 npm」。要隔离：**计算、网络、密钥、制品边界**。

**解答**  

1. **计算**：每次构建独立容器或微 VM，只挂本次 clone 的目录，构建结束销毁，不复用脏盘。  
2. **网络**：默认禁访 VPC / 云内元数据 IP；出网白名单 npm registry、GitHub、必要的镜像。需要访问私有 API 的再开明确 egress。  
3. **密钥**：只注入该环境（Preview/Production）声明过的 env；构建日志打码（`AKID*`、`password=`）。Fork PR 默认不注入敏感 env。  
4. **制品**：平台只收 Output 约定目录（static / functions / routes），不要把整个容器文件系统当部署物，避免把 `.env`、SSH key 打进 CDN。  
5. **资源**：CPU/内存/时长上限，防挖矿把集群打满。

口答：**构建不是 CI 同学的电脑，是多租户运行不可信代码，默认当恶意软件来防。**

#### Preview 和 Production 都是 HTTPS，cookie 和数据会不会串？

**场景**  
生产域 `app.com`，预览 `feat-login-xxx.pages.edgeone.ai`。前端登录 cookie 写成 `Domain=.com` 或错误地写在父域。更常见：Preview 环境变量里 `API_URL` 仍指向生产库，测试同学在预览里点「删除订单」删的是真单。

**细节点**  
隔离有三层：浏览器 Cookie 作用域、环境变量注入、后端是否识别来源。只说「Preview 和生产是不同 Deployment」不够，Deployment 隔离的是**制品**，不是用户配错的 API 地址。

**解答**  

- Cookie：平台子域和生产自定义域不要设成同一个 parent domain。Set-Cookie 默认 host-only。文档写明不要 `Domain=.example.com` 覆盖到预览。  
- 环境变量：系统注入 `PAGES_ENV=preview|production`。支付、短信、主库 URL 允许标成 **仅 Production**；Preview 构建拿不到这些键，会在构建期失败而不是默默打到生产。  
- 产品规则：模板里 Preview 默认接 sandbox。平台拦不住用户把生产 URL 填进 Preview，但可以在控制台对「Preview 使用了 Production 作用域变量」打强警告。  
- 预览链接默认公网可读时，未发布功能和 Preview token 会随 URL 传播，企业项目要密码墙 / SSO，鉴权在边缘解析 Host 之后、读文件之前。

#### 自定义域怎么防止别人把我的域名 CNAME 到他的项目？

**场景**  
攻击者在自己的 Pages 项目里添加 `www.victim.com`，并诱使（或等你配错）DNS CNAME 到 Pages 入口。若平台只认 CNAME、不认所有权，证书可能签到攻击者项目上，流量进他的 Deployment。

**细节点**  
Host 是查找键。谁拥有这个 Host，谁就拥有这个站点的流量。必须 **DNS 所有权证明** 和 **一 Host 一项目**。apex（裸域）和 `www` 要当成两个 Host 分别校验，但业务上通常一对一绑定同一项目。

**解答**  
添加自定义域时生成随机 TXT（或要求 CNAME 到 `verify-{token}.pages.xxx`）。定时探测，通过才：签发证书、写入别名。未通过的 Host 请求不要落到「碰巧同名的项目」。

同一 Host 不能绑两个项目；后绑者失败。证书用 HTTP-01 / DNS-01，签发完成前别名不要切到该 Host，否则用户浏览器报证书错误比 404 更难看。

### 边缘运行时

#### 预览域名那么多，Host 查找用什么结构？会不会每次回源数据库？

**场景**  
每个项目 × 每条分支 × 每次 commit 都可能有 Host。运行一年后别名条目到百万。用户请求必须在边缘数毫秒内完成 Host → Deployment ID，不能每次打控制面 MySQL。

**细节点**  
DNS 不能为每个预览打一条 A 记录。查找必须是 **泛解析 + 应用层 Host 表**。面试官听：热路径数据结构、缓存、过期删除（retention），否则元数据和存储账单无限涨。

**解答**  
`*.pages.xxx` 一张通配 DNS + 一张通配证书，所有预览进同一边缘入口。应用层：`Host` 字符串查别名表得到 `{deploymentId, projectId, env}`。表放在边缘 KV / 各 PoP 内存 LRU，miss 再拉控制面，回填。生产域和自定义域同样走这张表。

Retention：合并关闭的 PR、超过 N 天的预览，删别名和制品，部署 URL 也可以按策略 410。热路径禁止 SQL。控制面可以是 Postgres，但只作为权威源，不是请求路径。

#### 函数冷启动和 SSR 首字节，默认策略怎么选？

**场景**  
营销落地页用 Next，其实全是文档内容，适配器却把所有 path 打进 SSR 函数。冷启动 300ms+，费用按执行时间涨，CDN 形同虚设。另一个极端：所有 API 也 SSG，用户提交表单看到的是构建时的死数据。

**细节点**  
架构策略是 **默认静态、按需动态**。Middleware 在缓存前跑，它的成本乘在每一个请求上，包括本该 10ms 出站的 CSS。

**解答**  
适配器读清单：能 SSG/ISR 的进 CDN；真正 per-request 的（登录后 dashboard、webhook）进函数。ISR 用 TTL + 后台再生成，兼顾新鲜度和首字节。

Middleware 只做地理、登录 cookie 有无、A/B 分流，禁止在里面访问主库。重查询放函数，并让函数响应可缓存时写 Cache-Control，让下一跳打到 CDN。

给业务的口径：首屏能预渲染就预渲染；边缘函数不是免费的 Node 主机。

#### ISR 同时一万个请求打同一个过期 path，会不会把源打爆？

**场景**  
首页 ISR 60s。TTL 到期瞬间，大促流量打在同一 URL。若每个 miss 都调一次函数回源，函数并发和下游 CMS 一起爆。

**细节点**  
这是缓存击穿 / 惊群。CDN 普通 miss 已经会打源；ISR 还要「边过期边生成」。没有 **request collapsing**（同一 key 只放行一个生成者），平台会自己 DDoS 自己。

**解答**  
对 `(deploymentId, path, cacheKey)` 加锁或单飞：第一个 miss 执行函数，其余等结果或先返回 stale（stale-while-revalidate：先吐旧 HTML，后台生成）。生成失败要有负缓存短 TTL，避免错误风暴一直打函数。监控「回源 QPS / 边缘 QPS」比，突然升高就是 collapsing 没生效或 TTL 设太短。

#### 流式 SSR 超时了，已经写出一半的 HTML 怎么办？

**场景**  
React 流式渲染已经把 shell 和一部分 RSC 刷到浏览器，函数 `maxDuration` 到了。连接被 RST，用户看到半页转圈。监控里有的算 200（因为已经写了 status），有的算 504，值班对不上。

**细节点**  
流式响应在写出 `200` 和 headers 之后，**不能再改成 500**。超时策略、如何结束 chunk、监控口径要单独设计。

**解答**  
墙钟一到：停止函数、flush 结束帧、关掉连接，不要让 worker 僵死占着并发额度。能写错误边界就在流里插入错误 UI，不能就中断。超时阈值要按「页面可完成」来设，而不是随便 10s。

监控拆开：`function_timeout_while_streaming` vs `function_5xx_before_headers`。前者是产品体验问题（半页），后者是网关/代码错误。日志带 Deployment ID、path、已写出字节数。

### 适配器

#### Next 小版本一升，线上大面积 500，责任在谁？兼容性怎么定？

**场景**  
用户把 Next 15.0 升到 15.2，构建成功，线上 App Router 500。issue 开给你：「Pages 不兼容」。其实是清单字段改了或 server runtime 假设了 Node API。老板问：我们要承诺跟到 canary 吗？

**细节点**  
面试官要的是 **兼容性政策**，不是「我们会修」。平台保证的是契约（Output + 清单翻译），不是框架本体。成本在适配器和模板回归，要有矩阵和灰度。

**解答**  
对外承诺：支持的主版本列表（如 Next 14.x / 15.x 的最新 patch），以官方模板 + CI 每晚构建为准。不承诺任意 canary。

对内流程：框架发版 → 先跑官方模板和混合渲染模板 → 适配器改翻译逻辑 → 灰度一批真实项目 → 文档写 breaking change。构建期能发现的（清单缺失、不支持的 Node API）**失败在构建**，给出「请锁版本或等适配器」而不是上线 500。

责任划分：清单能译但 runtime 行为变了，适配器跟；用户用了未声明的实验 API，归用户。口答要有「矩阵 + 先模板后放量」，不要说「我们会尽快支持所有 Next」。

#### 本地 `next start` 正常，Pages 上 redirect 到 localhost / 变成 http，根因是什么？

**场景**  
登录成功后 `redirect('/')` 跳到 `http://localhost:3000`，或生成的 canonical、OG 图片 URL 是内网地址。构建日志全绿。只在平台域名下出现。

**细节点**  
这是 **请求适配** 不是构建。框架用 `request.url` / `headers.host` / `x-forwarded-proto` 拼绝对 URL。边缘 TLS 终结后，函数里看到的常常是内部 HTTP 和内部 Host。

**解答**  
包装层必须把用户访问的公网 URL 还原成框架入口：

- `Host` = 浏览器地址栏的 Host（自定义域或预览域），不是存储桶域名。  
- `x-forwarded-proto=https`（边缘已终结 TLS）。  
- `x-forwarded-for` / 平台 geo，供中间件。  
- `request.url` 用公网 origin + path + query，禁止 `http://127.0.0.1:0/...`。

排障：对比本地与线上同一 path 的 302 Location 头。Location 里出现 localhost 或 http，几乎一定是包装层。构建搬运只保证文件在，不保证框架以为自己在公网。

#### 为什么不自己实现一套 Next runtime？

**场景**  
有人提议：别搞适配器了，在边缘实现 `getServerSideProps` 和 App Router，用户无痛。或反过来：让用户必须按我们的目录写 Worker，不支持 `app/page.tsx`。

**细节点**  
这是平台边界。自己实现 runtime = 永远给框架打工；只给 Worker = 不是开发者产品。正确切分是 **原语稳定、适配器可变**。

**解答**  
边缘代理只认：静态、函数、路由表。Next/Nuxt/Astro 的语义留在它们官方 server 产物里，适配器负责搬文件、包函数、写路由、套包装层。框架升级改适配器，不改全球边缘。加框架 = 加适配器。代价是每个框架要跟清单变化；收益是边缘代码路径只有一条。

### 排障与产品判断

#### 客户说首页 404，你作为值班架构怎么查？

**场景**  
「昨天还好好的，今天打开 www 是 404。」没有构建失败通知。可能是：别名指错、路由表 fallback 没配、Output 根本没这个文件、缓存了一次 404、自定义域指到了别的项目、函数抛错被网关映射成 404。

**细节点**  
没有 Deployment ID 的访问日志，这个平台等于没做可观测。排查顺序必须沿 **Host → 别名 → 部署 → 路由 → 存储**，不能先猜 Nginx。

**解答**  
建议固定顺序：

1. 这次请求的 `Host` 解析到哪个 `deploymentId`（访问日志必打这个字段）。是不是客户以为的那次生产？  
2. 该 Deployment 的路由表：`/` 是静态、函数还是 SPA fallback？有没有一条把 `/` 301 到不存在的路径？  
3. 存储：`/{id}/static/index.html` 或对应函数包在不在。构建产物清单里有没有这个 path。  
4. 缓存：是否缓存了 404（负缓存）。purge 后再看。  
5. 时间线：别名何时切的、最近一次成功构建 SHA、有没有人改自定义域。  
6. 若是函数：该 path 的函数日志、超时、包装层 Host 是否正确。

对客户可复述：「你现在生产指的是 SHA abc 的部署，这个部署里没有 index.html，因为构建 output 配成了 `dist/client`。」这才像平台排障，而不是「清一下 CDN」。

#### 如果让你在 20 人团队重做一版，砍什么？为什么这能说明你是架构师？

**场景**  
长沙公司没有边缘机房，三个前端，老板听完 Pages 想「我们也搞一个内部 Vercel」。面试官怕你把腾讯云那套原样搬过来。

**细节点**  
看 ROI 和依赖。Pages 完整形态依赖 CDN、边缘函数、证书、构建集群。20 人团队缺的是这些底座时，应先买云产品，自研只留差异。

**解答**  
最小闭环：Git 或 CLI 上传静态 + 不可变目录 + 一个子域名 + SPA fallback。预览可以用 `commit-{sha}.xxx`。不要第一期做：多框架 SSR 适配器、ISR 惊群、自研证书中台、模板市场。

有真实 SSR 需求再加「一个 Node 函数 + 一张路由表」，只适配团队在用的那一个框架。模板等内部第二个项目出现再抽。

口答：**大厂经验是见过复杂度上限，所以知道第一周不该上什么。**

#### 你讲的 Git、函数、模板里，哪些是「用了模型」而不是「做了 AI 平台」？

**场景**  
面试官听完五块模块，问：这些和现在的 AI 应用有什么关系？他要听的是 **你产品上的具体点用了模型或为模型负载做了能力**，不是一套 Gateway / Agent 叙事。

**细节点**  
对得上的只有：构建失败总结、建议构建命令、函数流式、CLI 套模板、对话类模板。对不上的不要硬讲（训练模型、统一模型网关——除非你确实做了）。

**解答**  
按模块答，各一句：

- Git：失败日志总结进已有 PR 评论；构建命令可从仓库内容建议。  
- 全栈：函数流式 + env 隔离密钥；对话页是验收，不是新产品。  
- 适配器：包装层透传 stream。  
- CLI：自然语言选模板，deploy 协议不变。  
- 模板：货架上有对话/生成，用来打通流式和 Key。  

若追问实现是否和某国外平台像：同类问题会得到同类解法（SSE 不缓存、Key 不进前端、模板一键带函数），那是产品细节撞车，不是照搬别人的 AI Cloud 包装。

#### 这个项目里你个人做过最难的一次决策是什么？

**场景**  
行为面试 + 架构面试的交叉。没有标准答案，但没有故事会被判成「只是参与」。

**细节点**  
要有：选项、你选的、代价、事后验证。不要用「我们团队一起讨论」糊弄掉你的判断。

**解答（请换成你的真事，下面是结构示例）**  

- **选项 A**：第一期只做静态 Git 托管，函数后置——上线快，但 Next 用户会说「不能 SSR，不是真竞品」。  
- **选项 B**：第一期就上 App Router SSR——周期长，适配器质量决定口碑。  
- 你怎么选、砍了什么范围（例如只保证 Pages Router SSG + 一个 Node 函数）、上线后数据（首批用户里静态占比、SSR 工单量）、若重来会不会改。

另外可准备：Preview 默认公开 vs 默认加锁；自定义域是否第一期就做。有数字更好。
