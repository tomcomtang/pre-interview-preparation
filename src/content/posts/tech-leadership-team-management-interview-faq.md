## 前端架构与性能追问（待补充答题要点）

1. 中后台系统 / 大屏可视化 / H5，遇到过最棘手的性能瓶颈是什么？怎么解决的？

回答示例（可直接背）：

在我看来，前端最棘手的性能问题，不是首屏加载慢，而是大型单页应用（SPA）在长时间运行后的内存泄漏（OOM）导致浏览器崩溃。

在腾讯云控制台项目中，用户通常会把页面挂在后台几天几夜不关。由于我们采用了微前端架构，用户在不同云产品（如音视频、COS）之间频繁切换，基座会不断地动态加载和卸载子应用的 JS/CSS。

棘手在哪里？

只要有一个子应用在卸载时没有清理干净全局的 `window.addEventListener`、没有销毁定时器，或者闭包引用了庞大的 DOM 节点（Detached DOM），内存就会像滚雪球一样增长。这种问题在本地开发时根本测不出来，只有在线上跑了几个小时后，页面才会突然卡死或崩溃。

我是如何解决的？（体现架构师系统性思维）

解决这个问题不能靠“抓壮丁”式地去查代码，必须从架构机制和基建上入手，我分了三步走：

1. 底层隔离（沙箱机制）：重写微前端基座的沙箱逻辑。利用 ES6 的 `Proxy` 代理了子应用的 `window` 对象；子应用所有的全局事件监听和定时器，实际上都挂载在 `Proxy` 内部的 `Map` 里。当子应用卸载时，基座会强制且自动地清空这个 `Map`，从物理层面切断泄漏源。
2. 自动化监控（APM）：在前端监控 SDK 中加入内存快照（Heap Snapshot）的采样上报。当检测到 `performance.memory.usedJSHeapSize` 连续 3 次呈阶梯式上涨且未回落时，自动触发告警，并记录当时的路由访问路径。
3. 研发规范拦截：在脚手架的 CI/CD 流程中引入 Puppeteer 进行自动化内存泄漏测试。在无头浏览器中模拟用户频繁切换菜单 100 次，如果最终内存差值超过阈值，直接阻断发布。

结果：通过这套组合拳，我们将腾讯云控制台的 OOM 崩溃率降低了 95% 以上，实现复杂系统的长效稳定运行。

2. 微前端（qiankun / 无界）落地时，遇到过样式冲突、JS 沙箱、依赖共享问题怎么处理？

回答示例（可直接背）：

核心模块一：变量隔离（打造“假 window”）

首先，我们绝对不能让子应用直接操作真实的 window。

创建 Fake Window：在子应用初始化时，我会为它创建一个空的纯对象 fakeWindow。

Proxy 拦截：然后，我用 Proxy 将 fakeWindow 包装成 proxyWindow。

读写代理（Get/Set）：

- set 拦截：当子应用执行 window.a = 1 时，set 钩子会拦截这个操作，把 a = 1 存入 fakeWindow，真实 window 完全不受影响。
- get 拦截：当子应用读取 window.a 时，get 先去 fakeWindow 查找；如果找不到（例如子应用调用了原生的 window.fetch 或 window.Math），Proxy 会走 fallback 到真实 window 返回值。

代码执行域（沙箱闭包）：

为了让子应用的代码强制在这个 Proxy 环境中运行，我们在加载子应用的 JS 代码时，会使用 new Function，并在执行域中注入代理对象，让全局变量查找被强制收敛到 proxyWindow。

核心模块二：上下文修复（解决 Illegal Invocation）

这是 Proxy 沙箱最容易踩坑的地方，也是架构师需要处理的细节。

当我们把真实 window 上的原生方法（例如 console.log、alert、fetch）通过 Proxy get 返回给子应用时，如果 this 指向丢失，会触发 TypeError: Illegal invocation。

底层解法：

在 Proxy 的 get 拦截器里，对返回的值做类型判断：如果返回的是函数，并且来源于原生对象方法，则在返回前进行 this 绑定。

做法是动态地用 .bind(realWindow) 把 this 强制绑定回真实 window，保证原生 API 的正常调用。

核心模块三：沙箱逃逸与白名单机制（应对复杂 SDK）

在复杂业务场景里，子应用往往需要引入第三方 SDK（音视频、埋点、地图等）。这些 SDK 可能会动态创建 <script> 标签插入 document.head，动态脚本脱离闭包执行时就可能逃逸沙箱。

解决思路分两层：

1. 全局变量白名单

   - 在 set 拦截中维护配置化白名单（例如 ['__TENCENT_RTC__', 'BMap']）。
   - 如果子应用设置的变量命中白名单，则允许放行写入真实 window，以保证 SDK 能正常工作。

2. 动态脚本劫持（DOM 劫持）
   - Monkey Patch document.createElement 和 document.head.appendChild。
   - 当检测到子应用试图动态插入 <script> 时，在基座侧拦截该请求，先 fetch 获取脚本内容，再在受控执行域中重新包裹执行，确保动态加载的第三方代码仍被沙箱管控。

核心模块四：副作用管控（避免内存泄漏与 OOM）

变量污染最多造成显示异常，但副作用污染会导致整个浏览器崩溃（OOM）。

例如：子应用注册 setInterval 或 addEventListener，卸载后如果没有清理，定时器与事件回调会在后台持续运行。

因此沙箱必须具备自我清理能力：

- 沙箱初始化时劫持 setTimeout、setInterval、addEventListener。
- 在沙箱内部维护 Timer Set 与 Event Listener Map，记录子应用注册的定时器 ID 与事件回调。
- 子应用 unmount / 卸载时调用沙箱 destroy：遍历集合，执行 clearInterval / removeEventListener，强制回收资源。

做到这一步，Proxy 沙箱才具备工业级稳定性，避免长时间运行的泄漏与崩溃。

3. 移动端 H5 / 小程序，白屏、卡顿、兼容问题（iOS / 安卓差异、低版本浏览器）怎么根因分析？

开场白（定调：架构师的系统化思维）

“移动端 H5 和小程序的运行环境极其复杂，面对白屏、卡顿和兼容性问题，靠‘猜’或者‘本地复现’是极其低效的。

我的根因分析方法论是：‘线上靠 APM（性能监控）数据定界，线下靠 Performance 性能面板定点，底层靠工程化基建预防。’

具体到这三类最棘手的问题，我是这样进行根因拆解和治理的：”

一、白屏问题（生死问题）：如何精准定界？

“白屏是移动端最致命的体验问题。排查白屏，我首先会把问题拆分为两类：‘资源加载型白屏’ 和 ‘代码执行型白屏’。”

1. 资源加载型白屏（网络与基建层）

现象：HTML 没拉下来，或者核心 JS/CSS 加载失败。

根因分析：通过监控系统查看该用户的网络状态和 CDN 命中率。常见原因是弱网环境下的 DNS 解析失败、CDN 节点异常，或者小程序的包体积超限导致下载超时。

高阶解法：除了常规的资源预加载（Preload/Prefetch）和分包加载，在架构层引入离线包机制（将核心 HTML/JS 预置在 App 客户端内）或者骨架屏（Skeleton），确保在极端弱网下用户也能看到 UI 轮廓，而不是纯白屏。

2. 代码执行型白屏（逻辑与框架层）

现象：资源都下载了，但页面依然是白的。

根因分析：通常是 JS 发生了未捕获的致命错误（Uncaught Error），导致 React/Vue 的渲染树（Render Tree）挂载失败。比如低版本浏览器遇到了未 Polyfill 的 ES6 语法（如 Promise.allSettled），直接抛出 SyntaxError 阻断执行。

高阶解法：通过全局劫持 window.onerror 和 unhandledrejection 收集报错堆栈。在 React/Vue 层面，强制要求在根节点和关键组件外层包裹 Error Boundary（错误边界）。一旦发生 JS 崩溃，降级渲染出兜底 UI（如：页面开小差了，点击重试），彻底消灭纯白屏。

二、卡顿问题（体验问题）：如何揪出性能刺客？

“移动端卡顿的本质，是‘主线程被长时间阻塞（Long Task）’或者‘GPU 渲染掉帧’。”

1. JS 逻辑阻塞（Long Task）

根因分析：通过 Chrome DevTools 的 Performance 面板（或小程序的性能 Trace 工具）录制火焰图。重点寻找执行时间超过 50ms 的长任务（Long Task）。通常是主线程处理了超长列表遍历、复杂正则匹配，或者一次性 setData 传递了过大的数据量。

高阶解法：长列表用虚拟滚动（Virtual List）；复杂计算利用 Web Worker 将算力转移到后台线程；小程序的 setData 严格遵循按需局部更新原则，绝不全量 Diff。

2. 渲染层卡顿（Layout Thrashing & 内存泄漏）

根因分析：如果火焰图中看到密集的紫色块（Recalculate Style / Layout），说明发生了强制同步布局（布局抖动）。例如在 JS 循环中频繁读取 offsetHeight 又修改 style.height。

当内存快照显示 DOM 节点数持续飙升，通常意味着发生了内存泄漏；再叠加频繁 GC，页面会出现更严重卡顿。

高阶解法：动画必须使用 transform 和 opacity，并开启 will-change 触发 GPU 硬件加速，坚决避免使用 top/left 做动画。同时严格管理闭包和全局事件监听，防止内存泄漏。

三、兼容问题（碎片化问题）：如何抹平系统差异？

“iOS 和安卓的差异，以及低版本浏览器的兼容，是移动端最让人头疼的暗坑。我的排查思路是特征检测优于 UA 嗅探。”

1. JS API 与语法兼容（低版本安卓重灾区）

根因分析：很多低端安卓机不支持最新 ES API（例如 includes 或 Proxy）。

高阶解法：在工程化层面配置 Babel preset-env，并设置 useBuiltIns: 'usage'。打包时根据目标浏览器列表（.browserslistrc）按需注入 Polyfill：兼容可控，避免包体膨胀。

2. CSS 与 UI 表现差异（iOS 重灾区）

经典暗坑排查：

- 时间解析 Bug：iOS 的 new Date('2023-01-01') 可能返回 NaN，需要统一替换为 2023/01/01 这类可解析格式。
- 安全区适配与底部小黑条：iOS 全面屏需使用 env(safe-area-inset-bottom)，否则底部按钮会被遮挡。
- 滚动穿透与橡皮筋：iOS 弹窗出现时，底层页面仍可滑动。通过动态给 body 添加 position: fixed 并记录恢复 scrollTop 来彻底解决。

高阶解法：PostCSS 配 autoprefixer 自动补全 CSS 前缀。对已知系统级 Bug 沉淀为团队移动端基础工具库（Utils），统一调用，避免重复踩坑。

总结陈词（升华：从救火到防火）

“总结来说，面对移动端这些疑难杂症，排查只是救火，更重要的是防火。

作为架构师，我会推动两件事：

第一，建设完善的前端监控体系（APM），把 JS 错误率、白屏率、FCP（首次内容绘制）等核心指标大盘化，做到问题发生时有迹可循。
第二，在 CI/CD 流水线中加入自动化卡点，比如限制主包体积、使用 Lighthouse CI 做性能跑分。只有把规范沉淀到工具和流程里，才能从根本上提升移动端交付质量。”

5. 前端状态管理（Pinia/Vuex/Redux）在大型项目里怎么设计，避免混乱？

回答示例（可直接背）：

在大型项目中，状态管理走向混乱的万恶之源，就是“没有对状态进行分类，把所有的状态都塞进 Redux 或 Pinia 里”。

框架只是工具，真正决定项目可维护性的是架构设计和数据流向规范。为了避免大型项目中的状态混乱，我会从以下四个维度进行系统性的设计：

核心策略一：状态分类与剥离（最重要的一点）

首先，对前端状态进行严格分类，坚决抵制“全局垃圾桶”模式。我将状态分为三类：

局部 UI 状态（Local State）：比如弹窗的开关、表单的输入值、Tab 的切换。规矩：绝对不允许进入全局 Store，必须留在组件内部（useState / ref），随组件销毁而销毁。

服务端状态（Server State / Cache）：比如从接口拉取的商品列表、详情数据。规矩：剥离出全局 Store。过去习惯把 API 数据存入 Redux，导致写了海量 Action 和 Reducer（样板代码灾难）。现在引入 React Query / SWR（或 Vue Query）专门接管服务端状态：自带缓存、重试、轮询等机制，直接砍掉 Store 里冗余代码。

客户端全局状态（Client Global State）：比如当前登录用户信息、全局主题（Dark Mode）、跨页面的购物车数据。规矩：只有这类跨组件、跨路由共享的纯客户端数据，才允许进入 Pinia 或 Redux。

核心策略二：按“业务领域”划分模块（Domain-Driven Design）

当确定哪些数据该进入 Store 后，下一步是 Store 结构设计。很多老项目喜欢按技术职责划分（actions.js、reducers.js），大型项目中往往会变成高耦合灾难。

我会借鉴领域驱动设计（DDD）思想，按业务领域（Feature/Domain）拆分 Store。比如：

userStore（用户域）
cartStore（交易域）
appStore（全局配置域）

Pinia 支持这种扁平化模块设计（Setup Store），每个 Store 独立自治。Redux 侧则用 Redux Toolkit 的 createSlice，将 State、Reducers 和 Actions 聚合在一个文件里（Ducks 模式），做到高内聚、低耦合。

核心策略三：引入“防腐层”（Selectors / Getters），解耦 UI 与数据

大型项目最怕的是后端改了数据结构，前端几百个组件跟着报错。

规矩是：组件绝对不允许直接读取深层 State（例如 state.user.profile.avatar）。必须通过 Redux 的 reselect 或 Pinia 的 getters 来取数据。

Getter/Selector 充当组件与底层数据之间的“防腐层（Anti-Corruption Layer）”：字段映射只需要在 Getter 里改，上层 UI 完全不需要动。

核心策略四：严格管控数据修改（单向数据流）

状态混乱的另一个表现是“不知道数据是在哪里被改掉的”。

在 Vue/Pinia 中，虽然允许直接修改 state，但在大型项目里我会开启严格模式或在团队规范中强制：所有复杂业务逻辑与状态变更必须封装在 Store 的 actions 中，组件只调用 Action，不允许在组件内部拼装或修改全局 State。

在 React/Redux 中，Redux Toolkit 天然强制单向数据流，但我会进一步规范 Action 命名，采用 [Domain]/[Event] 格式（例如 user/loginSuccess），让 Redux DevTools 中的数据流向一目了然，方便追查来源与影响范围。

总结陈词（一锤定音）

在大型项目治理状态管理，我的核心心法是：

- 用 React Query / Vue Query 接管接口数据，给 Store 疯狂瘦身
- 用领域驱动（DDD）拆分 Store 模块
- 用 Selectors/Getters 建立防腐层，保护 UI 组件
- 严格收敛修改权限，坚持单向数据流

只要守住这四条底线，无论项目膨胀到多大、底层用 Pinia 还是 Redux，状态管理都能保持清晰和健壮。

6. 跨端方案（小程序 / uni-app / Taro）选型依据是什么？踩过哪些坑？

回答示例（可直接背）：

开场白（定调：理性的技术决策者）：

在跨端方案的选型上，我始终认为没有绝对完美的框架，只有最适合当前团队和业务阶段的方案。业界常说“一套代码跑多端”，在实际落地时往往会变成“一套代码，多端打补丁”。

因此，我的选型依据绝不是盲目追新，而是基于团队技术栈、目标产物矩阵以及性能要求这三个维度综合评估。

至于踩坑，跨端框架的坑主要集中在包体积、生命周期错乱和底层 API 差异上。具体我会这样思考和处理：

一、选型依据（展现技术视野与业务思维）

如果让我主导一个新项目的跨端选型，我会画一个决策矩阵：

1. 选 uni-app 的场景（重产物、重 Vue）

   - 依据：如果团队是纯 Vue 技术栈，且业务不仅需要小程序，还强依赖 App 端（iOS/Android）的输出。
   - 优势：uni-app 的生态极其庞大，底层的 App 渲染引擎（如 Weex/App-nvue）相对成熟。对需要快速铺开多端的中小型商业项目，交付效率最高。

2. 选 Taro 的场景（重矩阵、重 React/工程化）

   - 依据：如果团队以 React 为主，且业务形态是“小程序矩阵”（微信、支付宝、抖音、快手都要上），但对 App 端要求不高。
   - 优势：Taro 由京东开源，对 React 支持更原生；在大型企业级工程化（Webpack/Vite 定制）方面比 uni-app 更灵活。

3. 选 原生小程序 的场景（重性能、单平台）
   - 依据：如果业务只在微信生态内，且对首屏性能、包体积、复杂交互（如重度 Canvas、复杂动画）有极致要求。
   - 优势：任何跨端框架都有运行时开销；抛弃跨端框架直接用原生才能榨干性能。

二、踩过的核心坑与解法（展现真实经验）

在实际落地跨端项目时，我主要踩过并解决了三大类坑：

坑一：包体积爆炸（微信小程序 2MB 紧箍咒）
痛点：跨端框架会注入运行时垫片和框架源码，主包很容易突破限制，导致无法预览和发布。
解法：

- 严格分包架构：主包只保留 TabBar 与全局 Store，其余业务放进 subPackages。
- 公共依赖抽离：配置 Webpack/Vite 的 splitChunks，把多端复用的 lodash、moment 等拆到公共包；或替换为更轻量替代品（如 dayjs）。
- 静态资源上云：图片/大资源走 CDN，避免打包进代码。

坑二：生命周期与状态同步错乱（最易出 Bug）
痛点：跨端框架强行缝合 Vue/React 生命周期与小程序生命周期，导致“页面返回 A 后不刷新”的现象（因为页面未销毁，只触发了 onShow）。
解法：

- 团队规范明确：初始化请求写在 onLoad（或对应跨端 hook），每次曝光必须刷新的数据写在 onShow。
- 避免跨端组件内部滥用 DOM API（小程序端没有 DOM 树，会直接崩溃）。

坑三：UI 表现不一致与条件编译地狱
痛点：H5 的刘海屏/滚动行为、小程序的胶囊按钮/App 的状态栏等差异，容易通过 #ifdef 写到核心逻辑里，最终变成意大利面条维护地狱。
解法：

- 差异隔离：核心业务逻辑绝不写条件编译；把差异封装到底层的 Hook/基础组件/私有 Utils。
- 例如封装 <NavBar>：组件内部处理胶囊高度、沉浸式状态栏等差异，业务侧调用无感。

总结陈词（升华：架构高度 + 工程落地）

总结来说，跨端选型选的是“团队基因与业务边界的契合度”。
而要填平跨端框架的坑，不能只靠框架更新。作为架构师，我会建立“跨端工程化基建”：统一 UI 组件库、抹平 API 差异的底层 Utils，以及严格的 ESLint 规范。
只有把差异隔离在底层、把约束固化到工具与流程里，才能真正享受到跨端框架带来的研发提效。
