> 这份稿是面试时的**主陈述底稿**，不是功能清单。目标岗位是架构师 / 前端技术专家：先讲判断，再讲契约，再讲取舍。量化数字一律用你能背书的口径替换。

## 0. 30 秒定位（先把人设立住）

腾讯云控制台不是一个业务后台，而是**上百个云产品共用的前端操作系统**。我的角色不是某个产品页的开发，而是这套操作系统的架构负责人：把「壳层怎么跑、产品怎么接、版本怎么发、质量怎么管、跨产品能力怎么复用」做成一套可规模化的平台。

一句话收口：

> 我做的是控制台的**控制面与数据面**。野鹤是控制面，决定每个产品在国内站 / 国际站、各语言、白名单下该加载什么；控制台运行时是数据面，按这份配置动态装载 JS / CSS / 菜单 / SDK。脚手架、发布审批、灰度回滚、监控告警、质量周报，都是围绕这条契约转的。

## 1. 3 分钟主陈述（可直接说）

在腾讯云，我负责控制台前端底层生态。控制台域名是 `console.cloud.tencent.com`，用户进来后可以在 COS、音视频、CVM 这些产品之间切换。每个产品有自己的菜单、页面和发布节奏。如果做成一个巨石仓库，发布会互相卡住；如果完全放养，体验会割裂，线上问题也找不到归属。

所以我把问题拆成三层。

**第一层是运行时。** 壳层先拿用户身份和可访问产品列表，再按当前产品去拉配置：菜单、JS / CSS 地址、白名单、语言包、依赖的 SDK。切换产品时不是整页刷新成另一个站点，而是按配置装载对应资源。壳层统一做鉴权、导航、站点（国内 / 国际）、语言、埋点和全局错误捕获；业务只关心自己的页面。跨产品调用也走同一套机制：比如音视频上传要走 COS，不是把 COS 代码打进音视频包，而是在野鹤里声明依赖，运行时自动注入 COS 的 SDK，业务侧直接调 API。

**第二层是研发与发布。** 配置中心叫野鹤。产品负责人在上面配菜单、资源地址、白名单、国际站多语言，走审批后才能发布。发布、灰度、白名单验证、回滚，操作的是**入口配置指针**，不是覆盖 CDN 上的旧文件。配套脚手架把这条链路接到本地：`login` 做员工认证，`init` 按野鹤菜单生成工程和页面骨架，`dev` 按控制台代理规则联调，`build` 产出带 content hash 的资源，`commit` 自动在野鹤创建变更单，`scan` / `dict` 扫多语言词条。新业务接入，从「抄仓库、对文档、找人开权限」变成「拉配置、生成工程、本地验证、提交变更单」。

**第三层是质量和排障。** 平台统一收 JS 错误、资源加载失败、云 API 错误、点击和访问、首屏与资源耗时。错误要带产品、路由、资源版本，才能告警到对应团队。质量周报按周期打分排名，进步榜和落后榜是给业务负责人看的治理产品，不是给前端看的监控大盘。对难复现的客户问题，主人态允许内部人员用短时、可审计的 token 进入用户视角看配置，页面打水印，请求带操作人工号。另外还有自助接口：业务可以把一段受控代码登记成内部接口，中转云 API、做聚合裁剪，避免每个页面逻辑都堆在浏览器里，或为了一个 BFF 去排期一个后端服务。

这套东西的价值不在某个页面，而在于：**产品团队能独立发布，平台仍能保证体验一致、发布可控、故障可归因。** 架构师的工作是把组织规模问题，收成一套契约。

## 2. 面试时怎么画图（先画再讲）

先画两条线，比堆模块名更像架构师。

```text
                控制面（野鹤）
  产品配置 / 菜单 / 白名单 / 资源地址
  站点×语言×环境  审批 / 灰度 / 回滚
  SDK 依赖声明     变更单 / 负责人
                      │ 下发入口配置
                      ▼
用户 ─► 控制台壳层（数据面）
         鉴权 · 产品切换 · 站点/语言
         动态加载 JS/CSS/菜单
         按需注入 SDK
         统一埋点 / 全局错误
                      │
         ┌────────────┼────────────┐
         ▼            ▼            ▼
      产品 A        产品 B        产品 C
      音视频         COS          CVM
```

旁路再补三块，面试官问到再展开：

- **研发面**：脚手架 `login / init / dev / build / commit / scan / dict`
- **观测面**：错误、性能、云 API、资源加载、智能告警、质量周报
- **突破面**：主人态排障、自助接口（类边缘函数的 BFF）

口述时加一句：

> 野鹤改的是「下一步该加载哪一版」，壳层读的是「当前这一版」。历史资源留在 CDN 上。灰度和回滚是改指针，不是重新构建。

## 3. 核心判断（比技术方案更重要）

面试官听的是你怎么做决策。下面五条是这个项目的骨架，陈述时尽量落到其中两条。

### 3.1 巨石、微前端、iframe：为什么是配置驱动的壳 + 子应用

- **巨石**：上百产品线共享一个构建和发布窗口，谁也不敢发。
- **纯 iframe**：隔离最干净，但壳与业务的导航、登录态、主题、埋点都要桥接，体验和性能都差，跨产品 SDK 更难做。
- **配置驱动微前端**：产品独立构建、独立发布；壳负责生命周期和公共能力；**加载什么不写死在壳里，而由野鹤按身份、站点、语言、白名单下发**。

要点：微前端解决的是**组织协作和发布解耦**，不是为了用 qiankun。隔离方案可以演进，契约必须先稳定。

### 3.2 控制面 / 数据面，而不是「又做了个后台」

野鹤如果只是 CRUD 配菜单，那是运营后台。它真正的位置是控制面：

- 配置是多维的：国内站 / 国际站 × 中英日韩 × 产品 × 环境 × 白名单。
- 发布是有状态机的：草稿 → 审批 → 灰度 / 白名单 → 全量 → 可回滚。
- 运行时只消费**已生效的入口配置**，不在浏览器里拼业务规则。

配置爆炸不能靠笛卡尔积硬存。实际是**默认配置 + 站点覆盖 + 语言覆盖 + 白名单覆盖**，运行时做一次合并。面试时讲「覆盖而不是复制」，比讲表结构更有深度。

### 3.3 前端发布的本质是「入口与资源解耦」

- 构建产物带 content hash，只增不改，CDN 上旧文件始终可访问。
- `index.html` / 壳不写死业务 JS 路径，先请求入口配置。
- 灰度：按 UID、租户、地域、白名单返回不同 hash。
- 回滚：把生效指针拨回上一稳定版本，下一轮刷新即生效。

秒级回滚的前提是：**资源不可变，配置可变。** 没有这层，回滚就要重新构建、重新上传，那是发布系统，不是运行时治理。

### 3.4 SDK 是运行时联邦，不是 npm 依赖

音视频依赖 COS，如果走 npm：

- 版本升级要两边一起发；
- COS 热修无法单独推到已上线的音视频；
- 公共依赖（React 等）容易重复打包或版本冲突。

野鹤里把某产品的一部分能力登记为 SDK。消费方声明依赖后，壳在加载该产品时注入 SDK 资源，业务代码调的是 SDK 暴露的 API。思想上接近 Module Federation：Host 是壳，Remote 是 SDK，`shared` 约束基础库单例。

还要讲清楚边界：SDK 只暴露**稳定、可版本化的能力面**，不是把整个 COS 控制台塞给别人。版本冲突时，优先协商主版本；协商不成再允许 side-by-side，并计入质量成本。

### 3.5 质量必须变成组织杠杆

监控大盘只有平台团队看，改变不了上百条产品线。所以要有：

- 统一口径（同一套埋点维度、同一套错误归因）；
- 告警路由到产品负责人，而不是一个大群；
- 周报打分、进步榜 / 落后榜，让业务负责人看见自己的位置。

这是技术治理产品化。架构师的产出不只是系统，还有**让系统被用起来的机制**。

## 4. 模块深讲（按面试官兴趣展开，一次只挖一个）

### 4.1 控制台运行时：切换产品时到底发生了什么

1. 进入控制台：鉴权，拉取账号可访问的产品列表（权限与商业化开通状态都在这里过滤）。
2. 定位当前产品：URL、上次访问、默认产品。
3. 拉该产品在当前**站点 + 语言 + 环境**下的生效配置：菜单树、JS / CSS、用户侧开关（白名单）、SDK 依赖。
4. 壳装载资源，把上下文交给子应用：产品 ID、站点、语言、菜单路径、资源版本。
5. 子应用按菜单渲染；壳继续管顶栏、产品切换、主题、登出。

切换产品时要处理的不是「再 load 一个 script」，而是**上一个子应用的卸载**：全局事件、定时器、样式、路由监听。长会话场景下，泄漏会在用户挂机几小时后变成 OOM。面试若追问性能，就落到这里：沙箱记录副作用，卸载时强制回收；监控侧看 `usedJSHeapSize` 是否阶梯上涨。

样式隔离优先约定（CSS Modules / 命名空间），遗留系统再用运行时加前缀或 Web Component。不要一上来吹 Shadow DOM——React 合成事件会受影响，要有代理方案。

### 4.2 野鹤：配置、审批、灰度、回滚

配置对象可以记这张表，方便口头列举：

| 维度 | 配什么 | 为什么单独存在 |
| --- | --- | --- |
| 站点 | 国内站 / 国际站 | 合规、域名、可用产品不同 |
| 语言 | 中 / 英 / 日 / 韩 | 国际站菜单和文案不能混用一份 |
| 资源 | JS / CSS 地址与版本 | 发布的真正载荷 |
| 菜单 | 树、权限点、路由 | `init` 和运行时导航的同源数据 |
| 白名单 | 人 / 账号 / 特性开关 | 灰度验证和内测 |
| 负责人 | 产品 Owner | 告警和审批路由 |
| 变更 | 状态机 + 操作记录 | 审计和回滚依据 |
| SDK | 提供方与消费方声明 | 运行时注入 |

审批流的意义：控制台是客户生产操作面，前端发布等同于生产变更。野鹤把「谁改了入口、谁批了、影响哪些站点语言」变成可审计事件，而不是在群里说一声。

灰度与白名单验证：先让内部号或指定客户打到新 hash，看错误率和关键云 API，再放量。回滚只改指针。

### 4.3 脚手架：把平台契约变成开发者日常命令

| 命令 | 解决什么 | 面试时怎么升维 |
| --- | --- | --- |
| `login` | 员工身份，后面所有命令才有产品权限 | 工具链的身份不是 Git 账号，是公司员工身份 |
| `init` | 按野鹤菜单生成工程和每个菜单的渲染骨架 | 菜单是单一数据源，工程结构是配置的投影 |
| `dev` | 本地联调，按控制台代理规则验证 | 开发环境逼近生产壳，而不是自己起一个假首页 |
| `build` | 产出不可变资源 | hash、拆包、公共依赖策略与运行时约定对齐 |
| `commit` | 在野鹤生成当前版本的变更单 | 本地构建和发布单是一次提交，避免「包发了单没建」 |
| `scan` / `dict` | 多语言词条扫描与替换 | 国际站是一等公民，文案治理要进工具链 |

`dev` 的关键不是热更新，而是**代理规则与生产一致**：壳的域名、cookie、产品切换、配置拉取路径，本地要能走到。否则开发同学测的是自己的 webpack dev server，上线才发现被壳包一层后路由错了。

词条：用 AST 抽 `t('key')` 这类调用；动态拼接无法静态穷尽，所以要 ESLint 禁止变量 key，再加运行时 miss 上报。架构手段是**规范 + 扫描 + 运行时补洞**，不是幻想解析器万能。

### 4.4 日志、错误、性能、智能告警

评估对象是「某个产品当前加载的那一版 JS / CSS」，所以每条数据都要带：

- 产品、站点、语言、菜单 / 路由；
- 资源版本（hash 或变更单号）；
- 浏览器与地区（国际站尤其重要）。

监控内容分层：

1. **正确性**：未捕获 JS、Promise 拒绝、JS / CSS / 图片加载失败、云 API 错误码与量。
2. **行为**：PV / UV、点击埋点（壳事件与产品事件同一套公共维度）。
3. **性能**：首屏、资源平均耗时，用来做质量分，不是只做一次性优化。

告警规则要能区分「单用户浏览器插件」和「该产品这一版挂了」。例如：同一变更单上，JS 加载失败或某云 API 错误率在短窗口超过基线，才打到该产品负责人。固定文案的页面错误（白屏骨架、网关统一错误页）可以做特征匹配。

壳上的全局错误捕获是兜底：子应用没 catch 的，平台仍能知道，并且能区分壳的问题还是业务的问题。

### 4.5 主人态：排障能力，也是高危能力

客户说「我这边菜单和你演示的不一样」，往往是白名单、国际站、权限或灰度命中差异。内部人员用自己的号登不进客户的数据面。主人态用特殊 token **模拟用户进入其控制台业务，只读地看实时配置和页面**。

必须主动讲安全，否则面试官会认为你只做了方便、没做约束：

- 短时 token，走内部审批，内网或办公网限制；
- 请求强制带操作者身份，网关全量审计；
- 页面水印（工号 + 时间）；
- 权限尽量只读，写操作另开更高审批；
- 模拟范围收敛到具体产品，而不是整个账号上帝模式。

### 4.6 自助接口：前端要数据主权时的受控 BFF

控制台页面经常要把多个云 API 聚成一个视图。每次都等业务后端排期会很慢；全部堆在浏览器又会把密钥、签名、裁剪逻辑暴露出去。自助接口允许业务登记一段跑在平台里的代码，中转云 API 再返回。形态接近边缘函数 / 内部 FaaS。

面试时重点讲**为什么能让业务自己写代码**：

- 登记与鉴权：接口有身份、配额、所属产品；
- 运行时隔离：不能 `eval` 进主进程；独立内存和 CPU 上限，无宿主机文件系统；
- 出网限制：只能打指定云 API，防止当跳板；
- 可观测：和产品错误日志同一套归属。

这是平台能力，不是开放任意 Node。你会在安全和效率之间划边界，这正是架构师的工作。

### 4.7 质量周报

输入是一周的错误率、资源失败、性能分、告警次数、回滚次数等；输出是分数、排名、进步榜、落后榜。对象是产品负责人，动作为表扬和整改。平台团队提供口径和工具，不代替业务改代码。

## 5. 高频追问（先说本质，再给方案，再讲坑）

### 「子应用怎么隔离？SDK 版本冲突怎么办？」

本质是：共享壳的体验，隔离失败半径。

- CSS：约定优先；遗留系统运行时前缀或 Shadow DOM（注意 React 事件）。
- JS：Proxy 沙箱记副作用，卸载时回收；隔离要求极高再评估 iframe + Web Component。
- SDK：Remote 运行时加载 + shared 单例；冲突先协商主版本，再 side-by-side，并计入质量分。

坑：Proxy 拦不全 `window` 的某些 API；iframe 隔离干净但和壳通信成本高。我们按产品线风险分级，而不是一刀切。

### 「灰度回滚真能秒级？」

能，前提是资源不可变、入口可配。回滚改的是野鹤里的生效版本。用户已打开的页还是旧运行时，下一轮刷新或壳的配置轮询才会切。要更快，可以让壳短间隔拉配置，或对致命错误自动拨回指针——后者必须防抖，避免错误风暴来回抖动。

### 「国际站多语言怎么保证不漏词条？」

扫描只能覆盖静态 key。动态拼接靠 ESLint 禁止，运行时 miss 上报补洞。菜单和文案都来自野鹤的语言维度，`init` 时就按语言生成，避免业务自己维护一份平行菜单。

### 「主人态和自助接口会不会把公司搞出事？」

会，所以这两项是带闸门的能力。主人态是破窗流程，不是日常登录。自助接口是带沙箱和出网白名单的 FaaS，不是内网任意执行。架构师要能把「方便」和「可审计」一起设计出来。

### 「这套东西太重了，我们团队就二十人，你也会这么干吗？」

不会。腾讯云是上百产品线和独立发布的组织约束，才配得上控制面。二十人团队我会分阶段：先监控和规范止血，再轻量脚手架提效，只有构建变慢或多人抢一个仓时才拆微前端。大厂经验的价值是见过复杂度的上限，所以更清楚什么阶段不该上重型系统。

## 6. 陈述节奏与人设

| 时长 | 讲什么 | 不要讲什么 |
| --- | --- | --- |
| 前 30 秒 | 操作系统、控制面 / 数据面 | 菜单有哪些字段 |
| 中间 2～3 分钟 | 运行时加载 → 野鹤发布 → 脚手架闭环 → 质量治理 | 把 8 个模块平铺念完 |
| 留白 | 「监控、主人态、自助接口我也可以展开」 | 生怕没说完而超时 |
| 追问 | 本质 → 方案 → 坑与妥协 | 只报名词：qiankun、Module Federation、isolated-vm |

简历可用的三句话（按事实改数字）：

1. 主导腾讯云控制台大前端基座：配置驱动的多产品微前端，支撑国内 / 国际站及多语言下的产品独立发布。
2. 设计野鹤控制面与配套脚手架，打通初始化、联调、构建、变更单、灰度回滚与 i18n 词条治理。
3. 建设控制台质量与排障体系：统一监控告警、跨产品 SDK 运行时注入、主人态审计排障与自助 BFF。

和其他项目一起被问时的收口：

> 控制台项目证明我能在**超大规模 B 端、强治理、强发布约束**下做平台；Pages 证明我能把类似的「契约 + 适配器 + 开发者工具」做成面向外部开发者的产品。一个对内提效，一个对外建生态，底层都是同一套架构习惯：先定契约，再规模化。
