## 招聘网站项目经验

**项目名称：** 面向多产品协同的云控制台微前端运行时架构与发布治理平台

**项目定位：** 面向大规模云资源的动态微前端架构与研发运营（DevOps）一体化平台，支撑上百个业务团队独立敏捷发版，服务百万级企业用户。

**架构设计与核心技术：**

- **运行时微前端解耦：** 基于自研「壳-子应用」架构，实现控制台全动态按需装载（JS/CSS/菜单/白名单），支持多产品、多站点（国内/国际）及多语言（中/英/日/韩）无刷新切换；通过沙箱机制、全局副作用隔离与生命周期内存回收，彻底解决巨石应用内存泄漏与多团队发版冲突。
- **控制平台与发布阶梯：** 首创基于内容哈希（Content Hash）与灰度规则的动态控制面，建立「脚手架提交 → 变更单 → 真实环境预览 → 白名单验证 → 智能灰度观测 → 全量与秒级回滚」的标准化发布链路，实现生产环境「零覆盖」发布。
- **智能化研发流与资产复用：** 沉淀专属工程脚手架，打通从多语言自动扫描替换、组件外置（External）、公共用户信息 API 到跨产品 SDK 动态注入的全链路，结合 AI 代码生成与规范校验，大幅提升研发效能。
- **全链路观测与主人态诊断：** 构建带版本标识（Version Tagged）的统一埋点与错误捕获系统，精准定位问题归属；提供合规安全的主人态（模拟用户/Token 穿透）调试机制，秒级复现生产环境疑难杂症。

---

腾讯云控制台（`console.cloud.tencent.com`）是客户管理云资源的入口。用户在同一个站点里切换 CVM、COS、音视频等产品，每个产品有自己的菜单和页面，但登录态、顶栏、站点（国内 / 国际）和语言必须共用一套。

产品线多、发布节奏不同。做成一个巨石仓，上百个团队抢同一个发布窗口；做成各自独立的站点，客户要反复登录，跨产品能力只能复制代码。壳如果写死「某个产品加载哪一包 JS」，每接一个业务就要改基座、发基座。

这套系统是**配置驱动的微前端**：运行时是可切换产品的控制台壳，各产品是独立构建、独立发布的子应用；加载哪一版由野鹤按身份、站点、语言和发布规则下发，不写死在壳里。

```text
                控制面（野鹤）
  菜单 / 白名单 / JS·CSS 地址 / SDK 依赖
  站点 × 语言    预览 / 白名单 / 灰度 / 回滚
                      │ 下发生效配置
                      ▼
用户 ─► 控制台壳（微前端运行时）
         鉴权 · 产品切换 · 站点/语言
         装载子应用 JS / CSS / 菜单
         注入公共层、用户上下文、业务 SDK
                      │
         ┌────────────┼────────────┐
         ▼            ▼            ▼
      产品 A        产品 B        产品 C
```

子应用只渲染自己的菜单内容。壳负责生命周期和平台能力。微前端在这里解决的是组织协作和发布解耦：产品可以各自发版，客户仍然在同一个控制台里切换。

## 1. 运行时：壳与子应用

进入控制台后先鉴权，拉出这个账号开通了哪些控制台业务。切换产品时，按当前产品、站点、语言读取生效配置，再装载该业务的 JS、CSS、菜单和白名单，而不是整站跳到另一个域名。

壳把上下文交给子应用：产品 ID、站点、语言、菜单路径、资源版本。卸载上一个产品时回收全局事件、定时器和样式，避免长时间挂着页面后内存上涨。

样式优先用 CSS Modules 或命名空间约定；接不了构建约定的遗留页面，再在运行时加前缀。JS 用沙箱记下副作用，卸载时清掉。隔离按产品风险分级，不默认上 Shadow DOM。

配置不在浏览器里按维度硬拼。站点、语言、白名单会爆炸，控制面存的是**默认配置 + 站点覆盖 + 语言覆盖 + 白名单覆盖**，壳只消费已经合并好的生效快照。

### 公共 UI 与功能模块

按钮、表格、权限指令、请求封装如果每个产品仓再打一遍，包体积和体验都会裂开。公共功能模块和 UI 组件从子应用里剥出去，由壳加载一份；子应用构建时标成 external，运行时用壳上的同一实例。业务仓只打自己的页面代码。

剥出去的限于平台契约：设计体系、权限指令、埋点、请求封装。业务自己的组件仍留在业务包里。公共层单独走野鹤发布，可以预览、可以灰度，升级基座不等于每个业务重新发版。破坏性变更升主版本，避免一份公共层升级把所有产品一起打坏。

### 公共用户信息

登录态、UIN、主账号 / 子账号、地域、站点、语言、已开通产品列表，如果每个子应用自己调账号接口，请求会重复，口径也不一致。平台提供统一的用户上下文 API，子应用只读这份契约，不自己实现登录，也不解析主站 cookie。

主人态下，这套 API 返回的是被模拟用户的视图，子应用无感。国际站语言和国内 / 国际站点也从这里出。权限点仍由业务结合云 API 自己鉴权；公共信息只回答「是谁、在哪个站、开了哪些控制台产品」。

## 2. 野鹤：微前端的控制面

野鹤决定某个产品在什么规则下加载哪一版。「加载哪包 JS」不写在壳里。它按**产品 × 国内站 / 国际站 × 语言**配置菜单、JS / CSS 地址、白名单，以及负责人、变更记录、变更状态、错误与评分入口。国际站的中、英、日、韩是单独的配置维度。

构建产物带 content hash，只增不改，旧文件留在 CDN 上。壳不写死业务 JS 路径，每次按当前用户命中的规则读入口配置。预览、白名单、灰度、生产可以同时存在多份制品，靠规则选择，而不是覆盖同一条 URL。

发布顺序：

1. **变更单**：脚手架提交本次构建 hash，在野鹤生成发布单。控制台是客户生产面，谁改、谁批、影响哪些站点语言都要可审计。
2. **预览**：生产指针不动。用内部号或预览凭证，让壳拉取这一张变更单的 JS、CSS 和菜单，在真实控制台壳里点一遍。
3. **白名单**：指定账号走到新 hash，其余人仍走线上稳定版。
4. **灰度**：按 UID、租户、地域或百分比，让一部分真实客户吃到新版。观测看这一版的错误率和云 API，再决定放量或回滚。
5. **全量与回滚**：全量只改该产品的生效指针。回滚把指针拨回上一稳定 hash，不必重新构建。已打开的页面刷新后才切到新指针。

预览看的是「还没打到客户头上的那一版」；灰度看的是「一部分真实用户已经在用的那一版」。两者都是选版本，不是同一件事。

## 3. 接入脚手架

脚手架把控制面接到日常研发：

| 命令 | 作用 |
| --- | --- |
| `login` | 员工认证，从野鹤拉取该产品的控制台配置 |
| `init` | 按菜单生成工程，每个菜单一个渲染骨架，并默认外置公共组件、接入用户信息 API |
| `dev` | 按控制台代理规则联调，本地走壳的加载和用户信息，而不是另起一个假首页 |
| `build` | 打带 hash 的包，公共库不打进业务包 |
| `commit` | 在野鹤为当前版本开变更单，之后才能进预览、白名单、灰度 |
| `scan` / `dict` | 扫描并替换多语言词条，服务中、英、日、韩 |

新业务从抄仓库、对文档，变成拉配置、生成工程、本地验证、提交变更单，再走发布阶梯。

## 4. 跨产品 SDK

产品之间有直接依赖。音视频控制台上传要走 COS。如果打进 npm，两边的发布就绑在一起，COS 热修也无法单独推到已经上线的音视频。

野鹤允许产品把一部分能力登记为 SDK。消费方声明依赖后，壳加载该业务时自动注入 SDK 资源，业务 JS 直接调 SDK 的 API。壳是 Host，SDK 是运行时拉下来的 Remote，React 等基础库尽量只保留一份。

这和公共 UI 不是同一层。公共层是平台给所有子应用的底座；SDK 是某个云产品把能力提供给另一个云产品。SDK 只暴露稳定、可版本化的能力，不是把整个产品控制台塞给调用方。

## 5. 观测与质量

评估对象是「某个产品当前加载的那一版 JS / CSS」。

壳上有统一埋点和全局错误捕获。埋点带上用户、会话、产品、站点、语言、菜单路径和资源版本，壳层事件和产品内事件走同一条通道。错误侧收集未捕获异常、Promise 拒绝、JS / CSS 加载失败和关键接口失败，并带上产品、路由和发布标识，才能告警到对应业务团队，而不是混在一个大群里。

除此之外还有点击与访问、云 API 错误、首屏和资源耗时。平台给统一口径，业务可以补更细的业务错误。

质量周报把这些收成给产品负责人看的结果：周期内打分、排名、进步榜和落后榜，用来拉高控制台整体水位。

---

## 6. 主人态

客户侧的菜单、白名单和灰度命中，往往和内部账号不一致，问题难复现。内部人员经审批拿到短时 token，模拟进入该用户的控制台，只读查看他实际命中的配置和页面。请求带操作者身份，页面打水印，权限收在具体产品上。

主人态回答的是「这个用户实际加载了什么」。预览回答的是「还没全量的那一版长什么样」。

---

## 7. 自助接口

页面经常要聚合多个云 API。等业务后端排期慢，全部堆在浏览器里又不安全。平台允许登记一段受控代码，形态接近边缘函数：中转云 API、裁剪后返回。运行有配额、出网限制和隔离环境，不在主进程里 `eval`。错误归属和产品日志走同一套。
